# 第三章

## 理解网页浏览器

网页浏览器扮演着协调者的角色——为最终用户下载、渲染并执行你的网页应用。浏览器有能力让简单的代码看起来像一本光鲜的杂志文章（以苹果公司的 Safari 浏览器为例），或者像没有任何图片或高级功能的纯文本（以开源浏览器 Lynx 为例，可从`lynx.isc.org/`获取）。

本章将解释网页浏览器如何在内部运作，根据你编写的代码将用户看到的页面组合起来。同时，它也会描述网页如何通过网络连接到达你的浏览器，并指出若干可能阻碍性能的关键问题。

### 引擎：浏览器核心动力

在深入探讨浏览器内部工作原理之前，你需要了解一个重要区别：网页浏览器的用户界面与它在后台运行的代码之间的区别。让我们用汽车来类比。汽车引擎决定了它是一辆动力强劲还是高效节能的车。车身可能外观优美、设计精良，在静止时固然出色，但当你试图准时从 A 点到达 B 点时，它就没什么用处了。就像车身一样，设计精良的网页浏览器用户界面很少反映其内部运作。而如同引擎之于汽车引擎盖下，浏览器后台代码承担了繁重的工作。事实上，这些代码也被称为浏览器的*引擎*。

#### 渲染引擎与 JavaScript 引擎

大多数浏览器内部由两个主要引擎构成：

- 渲染引擎（也称为布局引擎），负责将 HTML 和 CSS 转换为屏幕上可见的页面
- `JavaScript`引擎，负责将你编写的`JavaScript`代码解释为浏览器能够理解并执行的内容

这些内部引擎与浏览器的用户界面是分开的。由不同公司、组织和个人编写的不同引擎，本质上决定了不同浏览器之间显示网页的差异。由于引擎与用户界面分离，从技术上讲，两个外观完全不同的网页浏览器可能使用相同的渲染引擎和`JavaScript`引擎。用户界面可以被视为包裹引擎的“皮肤”。事实上，有些网页浏览器基于相同的渲染引擎构建，如表 3-1 所示。

随着更大、更复杂的`JavaScript`驱动的 RIA 被开发并在网上提供，浏览器引擎需要能够将它们解读为用户可访问的内容。`JavaScript`引擎开发者致力于改进软件，以宣称自己的产品是市场上最快、最高效的浏览器。这些开发者的实际目标是确保最终用户体验 RIA 时，能获得类似桌面应用的体验。从许多方面来看，浏览器正在成为新的操作系统。诸如加载时间过长、浏览器卡顿以及用户操作响应缓慢等负面体验正慢慢成为过去。

#### `JavaScript`引擎性能基准测试

让我们回到汽车的比喻。正如你所料，并非所有引擎都生而平等。有些引擎比另一些更高效；有些对资源（内存空间、磁盘空间等）的需求更高；有些则速度更快。就像用数据、图表和原始数据来比较不同车型和制造商的表现与效率一样，在网页浏览器领域也有类似的比较。性能基准测试很常见，其测试结果备受网页开发者的关注。

这类比较存在一些争议，因为许多制造商会选择推广对自己产品有利的基准测试结果。这意味着，要全面了解性能全貌，需要警惕并仔细审视测试结果。

在撰写本书时，有四个主要的`JavaScript`基准测试套件被广泛用于比较不同浏览器中不同`JavaScript`引擎的性能：

- **SunSpider**：由 WebKit 引擎开发团队创建，是目前最常用的`JavaScript`性能基准测试套件。其测试仅专注于核心`JavaScript`功能，如函数调用、递归、循环和数学运算。然而，SunSpider 也包含针对特定应用的测试，例如通过字符串操作、解压和加密技术，从 JSON 格式输入生成标签云。该测试套件不包含任何用于衡量 DOM 交互性能的测试。

- **Dromaeo `JavaScript`测试套件**：这个`JavaScript`基准测试套件由 Mozilla 开发者创建，旨在允许他们在真实场景中测试自己的`JavaScript`引擎。它包含衡量核心`JavaScript`处理性能的测试，包括二叉树遍历、字符串与数组处理以及素数计算。该测试套件不包含任何 DOM 相关的测试。

- **Dromaeo DOM 测试套件**：除了核心`JavaScript`测试外，Mozilla 团队还创建了一个基准测试套件，用于测试浏览器内的 DOM 遍历与操作。这些测试对 RIA 开发者至关重要，因为许多网页应用通过`JavaScript`实现大量页面交互。DOM 交互速度越快，网页应用的感知性能就越快。遗憾的是，目前该测试套件无法在 IE 6、7、8 版本中正确运行，会在执行过程中触发`JavaScript`异常错误。

# V8 基准测试套件

`V8` 基准测试套件：该测试套件由谷歌创建。`V8` 是谷歌 `Chrome` 浏览器中使用的 `JavaScript` 引擎的名称。谷歌的开发者采用了一种新方法来应对 `JavaScript` 效率问题，即有效地将 `JavaScript` 代码解释为机器码级别——也就是你电脑中硅芯片能够理解的代码。虽然这使得 `Chrome` 在核心 `JavaScript` 性能方面非常高效——这也是 `V8` 基准测试所专门关注的——但在试图通过 `DOM` 与网页交互时，这几乎毫无意义，因为 `DOM` 依赖于 `JavaScript` 引擎和渲染引擎之间的高效交叉通信。

正如你所见，基准测试中涉及了政治因素。例如，你可能会怀疑 `SunSpider` 包含了一些在基于 `WebKit` 的浏览器上运行时能给出有利结果的测试，因为同一个团队同时构建了该浏览器和测试工具。当然，没有哪个基准测试的创建者声称偏爱某个特定的浏览器。然而，明智的做法是将所有基准测试工具的结果都考虑在内。让所有四个测试套件的综合结果来影响你对哪个 `JavaScript` 引擎性能最佳的判断。

每个测试套件都可以通过 `Dromaeo` `JavaScript` 性能网站（`http://dromaeo.com/`）运行，该网站将所有基准测试工具整合到一个集中的 `JavaScript` 性能测试中心。

每个基准测试套件会连续多次快速运行许多不同的测试，测量在给定时间范围内完成了多少测试，然后取结果的平均值，从而得出每个浏览器在每个测试套件上的最终性能数据。这些测试往往集中在 `JavaScript` 的两个主要方面：代码执行的原始处理能力和通过 `DOM` 与网页的交互。如果不测试这两个方面，你无法为网页中 `JavaScript` 的真实使用情况给出一个性能数据。

## 网页请求的剖析

你是否曾想过，从你在地址栏输入网址到完整页面出现在浏览器中之间发生了什么？在本节中，你将了解将一个 `URL` 转化为浏览器可以显示的内容所涉及的过程。

### `HTTP`：网络背后的通信标准

你的浏览器与目标网络主机之间的通信语言称为超文本传输协议（`HTTP`）。在这种语言或协议中，浏览器被称为*客户端*，网络主机被称为*服务器*。从你点击链接或在浏览器地址栏输入新 `URL` 开始，到页面在屏幕上加载完毕，客户端和服务器之间会来回发送消息。在这种语言中，请求消息从客户端传递到服务器，响应消息从服务器返回给客户端。

> **注意** 在浏览器地址栏中当前页面的网址前面，你会看到用于访问该 `URL` 的协议名称。在大多数情况下，它显示为 `http://`，代表 `HTTP`。但是，如果你正在浏览某些网站或页面，它可能会显示为 `https://`，代表 `HTTPS`，这是一种用于发送敏感数据的安全 `HTTP` 形式。其他协议包括 `ftp://` 和 `feed://`，分别用于浏览文件传输协议（`FTP`）站点和 `RSS` 新闻源。

在浏览器的地址栏中输入 `www.google.com`，让我们看看点击“转到”按钮后会发生什么。

### `HTTP` 请求消息

当你的浏览器请求一个 `URL` 时，会创建一个纯文本的 `HTTP` 请求消息，该消息将发送到服务器，请求服务器返回一个页面或文件。清单 3-1 展示了一个 `HTTP` 请求消息的示例。

**清单 3-1.** *针对 `www.google.com` 的 `HTTP` 请求消息示例*

```
GET / HTTP/1.1
Host: www.google.com
User-Agent: Mozilla/5.0 (Windows; U; Windows NT 5.1; en-GB; rv:1.9.0.3) ➥
Gecko/2008092417 Firefox/3.0.3 (.NET CLR 3.5.30729)
Accept: text/html,application/xhtml+xml,application/xml;
Accept-Language: en-gb,en;
Accept-Encoding: gzip,deflate
Accept-Charset: ISO-8859-1,utf-8;
Keep-Alive: 300
Connection: keep-alive
Cookie: PREF=ID=64637ffc707d92f4:TM=1222191214:LM=...
```

如果你不熟悉 `HTTP`，这可能看起来有些令人困惑。让我们分解一下，逐一了解请求消息中的每个*头*或条目，以便你理解发生了什么。该头的第一部分定义了用于发送此请求的操作或方法。

`HTTP` 请求消息中可提供八种操作，如表 3-4 所示。`GET`、`HEAD`、`OPTIONS` 和 `TRACE` 操作仅从服务器检索信息；而 `POST`、`PUT` 和 `DELETE` 操作会导致服务器上存储的数据发生更改。

**表 3-4.** *`HTTP` 请求动作*

| 动作 | 描述 |
|---|---|
| `GET` | 请求指定 `URL` 页面的正文内容，通常为 `HTML` 格式。 |

# HTTP 方法概述

-   `GET`：从指定资源请求数据。这是 Web 上最常用的操作。
-   `POST`：将数据发送回服务器，数据包含在请求消息本身中。此操作通常用于将 HTML 表单中的数据发送回服务器进行处理。

## HTTP 请求方法

| 动作 | 描述 |
|--------|-------------|
| `HEAD` | 与 `GET` 相同，区别在于所请求的 HTML 页面的正文不会随响应一起发送回。如果你只需要知道响应附带的元数据，而不是响应本身，或者你只是想证明特定 URL 上的资源确实存在，可以使用此方法。 |
| `PUT` | 用于更新服务器上的 URL 资源，在许多方面与 `POST` 类似，但仅当服务器允许对所请求的 URL 进行操作时才有效。 |
| `DELETE` | 如果服务器允许对请求的 URL 进行操作，则从服务器删除该特定 URL 上的资源。例如，你无法删除谷歌的主页。 |
| `TRACE` | 将服务器接收到的请求发送回发送方。这可用于显示客户端和服务器之间连接链中添加、更改或删除了哪些服务器或服务。 |
| `OPTIONS` | 返回特定 URL 上所有其他可用操作的列表，例如 `DELETE` 和 `PUT`。如果你将 URL 作为通配符 (`*`) 发送，则响应将包含 Web 服务器软件支持的操作列表。 |

## 示例 HTTP 请求

代码清单 3-1 中的示例 HTTP 请求以如下方式开始：

```
GET / HTTP/1.1
```

它执行一个 `GET` 请求，以便服务器返回所请求页面的 HTML 标记。此处指定的页面为 `/`，表示正在访问的网站的根目录。`HTTP/1.1` 表示此请求中所用语言的版本号。

### 请求头

`Host`: `www.google.com`

如果你不在消息中同时发送要访问的服务器的域名，那么指定要访问的 URL 为 `/`（根目录）是没有用的。HTTP 请求消息的 `Host` 头指明了该域名。

`User-Agent`: `Mozilla/5.0 (Windows; U; Windows NT 5.1; en-GB; rv:1.9.0.3) Gecko/2008092417 Firefox/3.0.3 (.NET CLR 3.5.30729)`

`User agent` 指的是用于访问网页的 Web 浏览器或软件。请求消息中的这个头条目不仅指定了浏览器名称及其版本号，还指定了浏览器运行的操作系统信息（本例中为 `Windows NT 5.1`，表示 Windows XP）、操作系统中设置的当前区域设置（`en-GB`，表示英国英语），以及浏览器或操作系统选择添加的任何其他数据。在代码清单 3-1 中，包含了 .NET 公共语言运行时 (`CLR`) 的版本。通过发送这些信息，服务器可以选择以任何方式使用这些信息——要么将其存储在日志文件中供后续统计分析，要么根据请求数据的浏览器软件类型，用不同的 HTML 标记进行响应。例如，如果服务器检测到用户代理来自移动设备，则可以在响应中发送更适合此类设备的简化版普通网站标记。不过在实践中，最好不要依赖这些数据，因为它很容易被伪造和篡改。

`Accept`: `text/html,application/xhtml+xml,application/xml;`

`Accept` 头包含浏览器接受的**多用途互联网邮件扩展** (`MIME`) 类型列表——这意味着浏览器知道如何将这些类型解释为人类可读的内容。MIME 类型 `text/html` 表示 HTML，`application/xhtml+xml` 表示 XHTML（尽管在撰写本文时某些 Web 浏览器不识别此类型），而 `application/xml` 表示 XML 内容。

`Accept-Language`: `en-gb,en;`

与 `Accept` 头类似，`Accept-Language` 头告知服务器浏览器中当前配置的语言和区域设置。然后，服务器可以根据此信息决定是否将特定语言或区域设置的数据发送回浏览器。在代码清单 3-1 中，有两个值：`en-gb` 表示英语和英国区域设置，备用为 `en`，仅表示英语语言，无特定地理区域设置。当然，如果正在访问的网站只有一种语言版本，或者网站开发者希望在不做任何假设的情况下将此选择权交给用户，服务器可能会选择忽略此信息。

`Accept-Encoding`: `gzip,deflate`

浏览器支持的特定内容编码类型通过 `Accept-Encoding` 头发送。如果服务器无法支持此列表中传递的编码类型，它将使用自己的标准编码。但是，如果它能够支持其中一种或多种编码类型，则允许将数据压缩后发送给浏览器，确信浏览器能够支持另一端的解压缩。压缩允许用更少的数据表示相同的内容，这意味着浏览器将更快地收到响应。

代码清单 3-1 中指定了两种不同的压缩算法：`gzip` 和 `deflate`。两种压缩算法都能产生有效的结果，尽管纯文本文件（包括 HTML、CSS 和 JavaScript 文件）的压缩效率远高于二进制文件（如图像）。这是因为纯文本文件通常包含大量空白字符，这些字符可以被非常高效地压缩。

`Accept-Charset`: `ISO-8859-1,utf-8;`

浏览器理解的字符集（即世界各种字母和符号的数据编码）在 `Accept-Charset` 请求头中声明。`ISO-8859-1` 字符集通常称为 Latin-1，可以表示大多数欧洲字符，包括带重音的字母。`UTF-8` 字符集较新，能够存储几乎所有世界语言的表示形式，使其用途极为广泛且强烈推荐使用。

`Keep-Alive`: `300`

`Keep-Alive` 头的值指定了客户端和服务器之间保持连接打开的持续时间（以秒为单位）。此持久打开的连接将用于后续的请求和响应，而不是每次都打开一个新连接。通过保持连接打开，无需每次都重新建立连接，这既耗时又消耗网络资源。代码清单 3-1 中指定的连接允许保持打开 300 秒，即 5 分钟。

`Connection`: `keep-alive`

`Connection` 头指定了此请求的首选连接类型。对于 `HTTP/1.1` 协议，`keep-alive` 是最常见的连接类型。

`Cookie`: `PREF=ID=64637ffc707d92f4:TM=1222191214:LM=...`

HTTP cookie 是存储在您计算机上的基于文本的小型数据片段。Cookie 由您访问的网站放置，以便网站能够存储和检索数据，从而为您提供个性化体验。例如，您可能访问 `http://www.google.com/` 并登录 Gmail 服务。登录过程会在您的机器上存储一个包含标识符值的 Cookie，Google 可以在您后续访问时检索该值以自动登录。

每个 HTTP 请求消息都会发送与正在访问的特定域名（网站地址）关联的、存储在计算机上的任何 Cookie。在代码清单 3-1 中，代表用户 Google 登录信息的标识符存储在 Cookie 中，并发送给服务器以自动将用户登录到其帐户。Cookie 可以让用户的生活稍微便利一些。但它们会随每个请求一起发送，因此应保持较小的体积。

# HTTP 响应消息

当服务器接收到请求消息并处理其数据后，会创建一个 HTTP 响应消息来包含处理结果。**清单 3-2** 展示了针对**清单 3-1** 中请求消息的服务器响应消息。

**清单 3-2.** *[www.google.com 的 HTTP 响应消息示例](http://www.google.com)*

```
HTTP/1.x 200 OK
Cache-Control: private, max-age=0
Date: Fri, 27 Mar 2009 12:42:14 GMT
Expires: -1
Content-Type: text/html; charset=UTF-8
Content-Encoding: gzip
Server: gws
Content-Length: 2520

<html><head>
... 谷歌主页的其余 HTML 内容 ...
</body></html>
```

接下来我们逐一讲解这些头部，确保你完全理解浏览器从服务器接收了什么信息，以及它如何使用这些信息。

### `HTTP/1.x 200 OK`

响应中的第一个头部让浏览器客户端知道，用于格式化消息其余部分的 HTTP 协议版本是哪个。在此例中，只要版本为 1 且任何次版本号都能理解该消息。版本号之后是一个状态码和简短描述，用于告知浏览器请求的结果是什么，这决定了消息其余部分的数据类型。这些状态码对于理解浏览器在收到响应消息时的行为至关重要，下一节将对其详细说明。

### `Cache-Control: private, max-age=0`

浏览器维护着一个本地文件缓存，会将近期请求过的文件存储在访问这些文件的计算机上，以避免重复下载，从而让终端用户的体验更流畅。`Cache-Control` 头部为浏览器提供了关于当前请求文件的某些参数，例如，告诉它缓存该文件多长时间。在此例中，`private` 告诉浏览器以及位于 Web 服务器和客户端之间的任何代理服务器，该文件是特定于请求它的用户的，也许是因为该文件已为该用户进行了个性化处理。如果没有这个设置，代理服务器可能会将其他用户的个性化主页发送给当前请求用户，造成严重混乱。`max-age` 属性告诉浏览器或代理服务器将文件缓存多长时间，单位是秒。在此例中，值为 `0` 确保每次都会从服务器请求一个全新的文件副本，这对于像谷歌主页这样的个性化网站是最佳的。其他文件，例如图片、CSS 和 JavaScript，理想情况下可能会设置更长的 `max-age` 值，以确保它们在每次请求新页面时都不需要被重新请求。

> **注意：** 将 `Cache-Control` 设置为 `no-cache` 会告诉浏览器不要将该文件存储在缓存中，从而强制每次请求时都从服务器重新下载相同的文件。

### `Date: Fri, 27 Mar 2009 12:42:14 GMT`

`Date` 头部的值仅指示响应消息发送的日期和时间。

### `Expires: -1`

`Expires` 头部指定了所发送文件被视为过期（或陈旧）的日期和时间，届时应下载新副本。值为 `-1` 表示内容已经太旧，从而强制浏览器下次从服务器下载全新的副本。

### `Content-Type: text/html; charset=UTF-8`

`Content-Type` 头部指定了此请求中发送内容的 MIME 类型。`text/html` 表示发送的内容是 HTML。如果是基于文本的内容，还可以在此头部中指定字符集。

### `Content-Encoding: gzip`

`Content-Encoding` 头部指示了应用于响应中发送内容的内容编码类型。服务器会监听之前提到的 `Accept-Encoding` 请求头部，并且只应以客户端支持的编码格式发送回内容。

### `Server: gws`

`Server` 头部将 Web 服务器软件的名称发送给客户端。值为 `gws` 表示使用了谷歌自己的 Web 服务器软件来生成响应。

### `Content-Length: 2520`

随此响应消息发送的文件内容大小（以字节为单位）在 `Content-Length` 标头中指定。

```
<html><head>
... Google 首页的其余 HTML 代码 ...
</body></html>
```

### 消息如何传输

现在我们已经介绍了 Web 通信消息的语言，接下来需要了解这些消息如何在浏览器和目标服务器之间实际传输。消息需要从浏览器所在位置传输到 Web 服务器所在位置，再返回，这个过程可能跨越全球。本节将解释这些消息如何从源头到达目的地而不会在途中丢失。

### IP 地址：互联网的电话号码

浏览器创建其 HTTP 请求消息后，需要将其发送给 Web 服务器。因此，首要任务是定位该 Web 服务器。以清单 3-1 中的 HTTP 请求消息为例，Web 服务器的域名`www.google.com`必须先转换为互联网协议（IP）地址，然后才能被定位。这种地址看起来像是一系列由点号（`.`）分隔的数字。例如`www.google.com`可能对应`209.85.171.99`。IP 地址帮助浏览器及其他连接互联网的系统找到将消息路由到目标 Web 服务器所需的信息。IP 地址就像是服务器的电话号码。

为了将人类可读的域名（也称为*主机名*）转换为数字序列，您的浏览器必须连接到一个在线数据库，称为域名系统（DNS）或*名称服务器*，其中包含主机名及其关联的数字 IP 地址信息。名称服务器的主要作用有两个：

**128**

- 人类可读的主机名比数字序列更容易记忆。
- 主机名和 IP 地址可以独立更新。

例如，Google 可以将其 Web 服务器迁移到世界另一端的另一台机器上，IP 地址也会随之改变。无需通过主机名来传达这一地址变更，Google 只需在 DNS 数据库中更新 IP 地址，让其指向新位置的 IP 地址即可。这使得系统对最终用户透明。

在深入探讨 DNS 系统的工作原理之前，理解 URL 的各个组成部分很重要。以 URL `www.google.com`为例，让我们用分隔点将地址划分，并依次查看每个部分，从最后一个开始逆向分析。

- **com**：任何网址最右侧的部分称为*顶级域*。您可能见过`.net`、`.org`等。DNS 系统首先使用 URL 的这一部分，将地址列表过滤为仅包含此顶级域内的地址。
- **google**：URL 的中间部分告诉 DNS 服务器在其`.com` URL 列表中定位`google`条目。系统实质上是过滤可用的 URL。
- **www**：URL 的第一部分涉及要访问的`google.com`站点下的特定服务器或子域。同样，列表已被有效过滤为仅包含该域下的服务器。

不要认为只有一个 DNS 服务器在积极处理来自全世界所有浏览器和联网设备的 IP 地址查询请求。目前存在 13 个根级 DNS 系统（每个系统由一组服务器集群组成以应对流量负载），不过公司或组织可以向其内部网络提供这些系统的本地副本，以加快查询过程。

根级 DNS 系统负责处理 URL 的顶级域和服务器部分，仅查找这一级别的 IP 地址。此后，请求被转发到该域的服务器——在本示例中，即`google.com`的 DNS 服务器。

DNS 数据库中的每条记录不仅包含 IP 地址，还包含域所有者的联系信息以及一些关键服务器的地址，包括本地名称服务器。

大多数组织至少在其网络上拥有自己的主用和备用名称服务器（Google 目前拥有四个名称服务器）。如果第一个服务器出现问题，请求将被重定向到第二个服务器，从而降低查询失败的可能性。根级 DNS 系统将`www.google.com/`的请求传递给 Google 的本地名称服务器，然后这些服务器返回名为`www`的本地服务器的确切 IP 地址，最终返回目标 Web 服务器的最终 IP 地址。

### 数据包：数据块

互联网上计算机之间发送的通信消息由称为*数据包*的小数据块组成。一个请求通常由多个数据包构成。

采用发送数据包而非一次性发送整个数据消息的主要原因是为了减少网络问题的影响。如果某个数据包未能送达，可以重新发送直到成功接收，而无需重新发送整个数据消息。此外，对于性能较低的计算机系统，较小的数据包比大的更易于管理，因为每个数据包仅需占用少量可用内存即可处理。

**129**

### 路由与路由器：互联网的交换台

一旦你的浏览器知道了最终目标服务器的 IP 地址，它就需要连接到该目标，以便向其发送请求消息并等待响应数据。被称为*路由器*的设备位于互联网上的每个主要流量枢纽处，负责执行连接和全球数据包的路由。这些设备维护着本地的*路由表*，其中包含关于如何将数据包从当前位置最佳地引导到更靠近 Web 服务器位置的信息，直到数据包到达目的地。

## HTML 页面的加载顺序

一旦浏览器收到页面请求的响应，它就会获取响应中提供的 HTML 标记并进行显示。本节将解释这是如何执行的，以及重新定位页面中某些 HTML 标签对其加载时间的影响。

一个 HTML 文档包含两个主要部分：头部（head）和主体（body），分别由`<head>`和`<body>`标签表示。浏览器通常会在响应消息中的数据仍在下载时就开始构建页面，从`<head>`部分开始，然后进入`<body>`部分。头部部分可能包含以下任何标签：`<style>`、`<link>`、`<script>`、`<meta>`、`<title>`和`<base>`。

除`<script>`之外的所有这些标签都只允许在`<head>`部分内，不允许在其他地方出现。这个规则告诉你，浏览器在渲染 HTML 的`<body>`部分之前需要了解些什么。如果你依次查看每个标签的描述，就应该明白为什么需要在处理`<body>`标记之前预先了解这些信息：

-   `<style>`：包含 CSS 样式定义，以便以自定义设计在页面上布局 HTML。浏览器需要知道如何在屏幕上显示标签之前进行布局，以防止出现难看的渲染效果。否则，浏览器会在应用自定义样式之前以默认样式绘制标签。`<style>`标签确保永远不会发生这种情况。

-   `<link>`：链接到外部数据。当引用外部样式表时，浏览器出于与需要知道`<style>`标签中的样式相同的原因，需要了解这些链接。当它适用于链接到站点内的其他文档时，它仅表示头部信息，与页面的主要内容分开。

-   `<meta>`：提供定义页面内容但独立于页面内容本身的数据。示例包括指定页面的关键字和描述，以供搜索引擎爬虫使用。也可以使用此标签执行与某些 HTTP 响应消息头值相同的操作——例如，为内容设置到期日期或指定内容类型。

-   `<title>`：指定页面的标题。这是出现在浏览器窗口标题、书签链接、搜索引擎结果和其他位置中的文本。

-   `<base>`：允许页面开发者为页面内容中指定的所有链接、图像和其他 URL 规定一个基础 URL。例如，如果`<base>`标签设置为指向`http://www.google.com/`，并且页面中的一个链接仅指定为`logo.gif`，那么浏览器将要查找的完整 URL 将是这两个 URL 的组合：`http://www.google.com/logo.gif`。

一旦浏览器读取了`<head>`部分并下载了其中所有必要的外部链接文件，它就可以开始顺序地、一个标签一个标签地读取和解析 HTML 文档的主体部分了。

## 页面性能

页面性能的一个重要方面是将该页面下载到 Web 浏览器所需的时间。如果你发现页面加载时间过长，可以尝试找出导致性能不佳的原因。

### 查看页面性能

有两个工具对于查看页面及其内容的实时下载时间非常有用：

-   最流行的工具是 Firefox 的 Firebug 插件。可以从`http://www.getfirebug.com/`下载 Firebug。

-   另一个选项是 Safari 4 中的网络时间线工具。要启用此功能，请打开浏览器的偏好设置页面，单击“高级”选项卡，然后勾选“在菜单栏中显示开发菜单”选项。然后，你可以通过选择“开发” ➤ “显示 Web 检查器”并选择“资源”选项卡来访问网络时间线工具。

这两个工具都允许你查看服务器响应请求消息所需的时间，以及下载文件所需的时间。

### 识别性能中的潜在瓶颈

我们都希望浏览器能始终以最高效率加载页面请求：尽可能快地下载每一点数据，并在接收到每一块数据时立即将其渲染到屏幕上。不幸的是，实际情况并非总是如此。

在本节中，我将揭示一些可能导致页面加载效率低下的潜在瓶颈。目前，我不会提供这些缺陷的解决方案或变通方法；但请放心，在后续章节中，我会向你展示如何尽可能多地解决这些问题。

### 引擎马力

本章前面部分，我们探讨了存在于 Web 浏览器中的渲染引擎和 JavaScript 引擎，它们负责将 HTML、CSS 和 JavaScript 格式的简单文件转换为功能完整、可交互的网页。不同浏览器的引擎基于不同的底层代码构建，因此它们具有不同的性能特征，这并不令人意外。

通常，随着新版本的发布，浏览器制造商会修改底层代码以增强引擎性能，从而提升引擎效率。这使得当前主流 Web 浏览器的性能比以往任何一代都要好上数倍。

一般来说，终端用户使用的浏览器版本越旧，他们所经历的渲染和 JavaScript 性能就越差。

### 用户的上传速度

大多数用户通过 ISP（互联网服务提供商）以非对称连接的方式接入互联网。这意味着大多数用户可用的下载带宽远大于上传带宽；这两种连接速度并不相同。

带宽与下载或上传数据所需的速度成正比。

你可能会想，请求一个网页时需要从你的计算机上传哪些数据。事实上，从被请求页面链接的每一个外部文件——每张图片、每个样式表和 JavaScript 文件——在下载之前，都需要构建一个新的 HTTP 请求消息并发送到服务器。如果你的页面链接了大量外部文件（无论这些文件大小如何），你可能会发现用户的网络连接达到了上传限制，并且需要等待之前的请求发送完毕后，才能发送新的请求。互联网速度一直在提升，所以这个问题正在缓解，但仍值得对页面进行调整，以减少那些连接速度较慢的用户（例如移动用户）所遇到的困扰。

### 并行连接限制

许多浏览器都对可同时与每台服务器建立的连接数量设置了内部限制。一个现代 RIA（丰富互联网应用）页面，尤其是设计复杂的页面，可能包含超过 50 个外部文件引用需要加载才能完整渲染。对并行连接数量的限制，显然会限制页面下载并显示给用户的速度。
```

HTTP 1.1 规范建议同时连接数限制为同时下载两个文件。Opera 和 Safari 浏览器将此限制提高到四个。IE 8 则将其提高到同时下载六个。这些限制显然会制约浏览器的性能。如果所有文件都能同时下载，页面就能更快地呈现给最终用户。

### 图片格式的选择

历史上，Web 上盛行三种图片格式：GIF、JPEG 和 PNG。这些格式彼此差异巨大。在为页面编码图片时，如果选择了错误的格式，或采用了低效的压缩设置，就可能导致图片文件体积超出必要大小。由于大多数网页中图片的数量远超其他类型的文件，因此文件格式的选择应作为首要关注点。

### 不必要的内容

文件体积越大，下载到浏览器所需等待的时间就越长。在构建标记时，请确保没有引用不必要的样式表或 JavaScript 文件，也没有在页面中包含大段的注释。包含了不必要的代码，就意味着你冒着将永远不会使用的数据下载到用户浏览器的风险，这会增加完整页面渲染所需的时间。

### 缓存设置

一些 Web 开发人员选择在其 Web 浏览器中禁用所有缓存，以便始终拥有自己文件的最新副本进行测试。然而，大多数终端用户会保持其缓存设置为默认值，这通常意味着决定哪些内容被缓存以及缓存多久的规则，取决于传输内容的 Web 服务器的响应头。调整服务器，使其仅发送与先前类似请求相比有所更改的内容，可以确保浏览器需要接收的数据更少，从而为最终用户带来更快的体验。

### 未压缩的文本文件与多余空白

在构建和编写基于文本的 HTML、样式表和 JavaScript 文件时，空白字符的使用可能很重要。制表符间距、换行符、空格和注释有助于使代码更易于阅读、理解和维护。

每个制表符、换行符和空格字符都是浏览器有效渲染页面所不需要的数据。如果你能移除这些不必要的数据，文件大小将会减小，从而下载速度也会更快。

大多数浏览器和服务器都支持压缩算法，通常是 `gzip` 和 `deflate`，这些算法在传输时会压缩数据大小并移除所有不必要的字符，然后在接收端解压数据。如果没有压缩，文件体积会比实际需要的大，页面下载时间也会受到不利影响。

### 总结

本章描述了从 Web 服务器请求页面并将其发送到浏览器，然后将该响应转换为网页的过程，并重点指出了若干对此过程的速度和效率产生不利影响的因素。

在下一章中，我将揭示如何通过对 Web 服务器和代码进行特定更改，从而显著提升 Web 应用的性能，为你的最终用户提供更好的体验。
