# 列入黑名单

## 404 未找到

请求的 URL 未找到任何内容。欢迎客户端日后再次尝试此 URL，届时该位置可能存在相应文件。

## 405 方法不允许

HTTP 请求消息中指定了不允许在指定 URL 上执行的操作。例如，如果请求消息试图对 Google 主页调用`DELETE`操作，您将收到此消息。

## 410 已移除

与`404 Not Found`相同，区别在于客户端不应再次尝试访问此 URL。如果客户端是搜索引擎爬虫，则应从索引中删除此 URL。

## 413 请求实体过大

请求消息过大，服务器无法处理。如果 HTML 表单向服务器提交的数据量超出其处理能力，则可能返回此状态码。

## 414 请求 URL 过长

如果服务器对 URL 的可接受长度设有限制，当请求消息中的 URL 超过此限制时，将返回此状态码。

**127**

## 500+ (服务器错误)

状态码范围为 500–599，表示发送的请求有效，但由于服务器问题，请求未能成功完成。这表示问题出在服务器端，而非客户端。表 3-8 列出了此范围内的常见状态码。

**表 3-8.** *表示服务器错误的 HTTP 状态码*

| 状态码 | 说明 |
|-------------|-------------|
| 500 服务器内部错误 | 最常见的状态码，表示服务器上发生了一般性错误。通常发生在请求的 URL 是服务器端脚本，且该脚本在运行时出错的情况下。 |
| 501 未实现 | 服务器无法理解或支持所请求的 HTTP 操作。 |

### 消息如何传输

现在我们已经介绍了 Web 通信消息的语言，接下来需要了解这些消息如何在浏览器和目标服务器之间实际传输。消息需要从浏览器所在位置传输到 Web 服务器所在位置，再返回，这个过程可能跨越全球。本节将解释这些消息如何从源头到达目的地而不会在途中丢失。

### IP 地址：互联网的电话号码

浏览器创建其 HTTP 请求消息后，需要将其发送给 Web 服务器。因此，首要任务是定位该 Web 服务器。以清单 3-1 中的 HTTP 请求消息为例，Web 服务器的域名`www.google.com`必须先转换为互联网协议（IP）地址，然后才能被定位。这种地址看起来像是一系列由点号（`.`）分隔的数字。例如`www.google.com`可能对应`209.85.171.99`。IP 地址帮助浏览器及其他连接互联网的系统找到将消息路由到目标 Web 服务器所需的信息。IP 地址就像是服务器的电话号码。

为了将人类可读的域名（也称为*主机名*）转换为数字序列，您的浏览器必须连接到一个在线数据库，称为域名系统（DNS）或*名称服务器*，其中包含主机名及其关联的数字 IP 地址信息。名称服务器的主要作用有两个：

**128**

- 人类可读的主机名比数字序列更容易记忆。
- 主机名和 IP 地址可以独立更新。

例如，Google 可以将其 Web 服务器迁移到世界另一端的另一台机器上，IP 地址也会随之改变。无需通过主机名来传达这一地址变更，Google 只需在 DNS 数据库中更新 IP 地址，让其指向新位置的 IP 地址即可。这使得系统对最终用户透明。

在深入探讨 DNS 系统的工作原理之前，理解 URL 的各个组成部分很重要。以 URL `www.google.com`为例，让我们用分隔点将地址划分，并依次查看每个部分，从最后一个开始逆向分析。

- **com**：任何网址最右侧的部分称为*顶级域*。您可能见过`.net`、`.org`等。DNS 系统首先使用 URL 的这一部分，将地址列表过滤为仅包含此顶级域内的地址。
- **google**：URL 的中间部分告诉 DNS 服务器在其`.com` URL 列表中定位`google`条目。系统实质上是过滤可用的 URL。
- **www**：URL 的第一部分涉及要访问的`google.com`站点下的特定服务器或子域。同样，列表已被有效过滤为仅包含该域下的服务器。

不要认为只有一个 DNS 服务器在积极处理来自全世界所有浏览器和联网设备的 IP 地址查询请求。目前存在 13 个根级 DNS 系统（每个系统由一组服务器集群组成以应对流量负载），不过公司或组织可以向其内部网络提供这些系统的本地副本，以加快查询过程。

根级 DNS 系统负责处理 URL 的顶级域和服务器部分，仅查找这一级别的 IP 地址。此后，请求被转发到该域的服务器——在本示例中，即`google.com`的 DNS 服务器。

DNS 数据库中的每条记录不仅包含 IP 地址，还包含域所有者的联系信息以及一些关键服务器的地址，包括本地名称服务器。

大多数组织至少在其网络上拥有自己的主用和备用名称服务器（Google 目前拥有四个名称服务器）。如果第一个服务器出现问题，请求将被重定向到第二个服务器，从而降低查询失败的可能性。根级 DNS 系统将`www.google.com/`的请求传递给 Google 的本地名称服务器，然后这些服务器返回名为`www`的本地服务器的确切 IP 地址，最终返回目标 Web 服务器的最终 IP 地址。

### 数据包：数据块

互联网上计算机之间发送的通信消息由称为*数据包*的小数据块组成。一个请求通常由多个数据包构成。

采用发送数据包而非一次性发送整个数据消息的主要原因是为了减少网络问题的影响。如果某个数据包未能送达，可以重新发送直到成功接收，而无需重新发送整个数据消息。此外，对于性能较低的计算机系统，较小的数据包比大的更易于管理，因为每个数据包仅需占用少量可用内存即可处理。

**129**

### 路由与路由器：互联网的交换台

一旦你的浏览器知道了最终目标服务器的 IP 地址，它就需要连接到该目标，以便向其发送请求消息并等待响应数据。被称为*路由器*的设备位于互联网上的每个主要流量枢纽处，负责执行连接和全球数据包的路由。这些设备维护着本地的*路由表*，其中包含关于如何将数据包从当前位置最佳地引导到更靠近 Web 服务器位置的信息，直到数据包到达目的地。

你可以使用计算机上已内置的软件，亲自查看数据是如何在你的浏览器和目标服务器之间路由的。如果你是 Microsoft Windows 用户，请加载命令提示符。为此，请选择“开始” ➤ “运行”。在出现的框中，键入`cmd`，然后按 Enter 键。在命令提示符窗口中，键入以下命令并按 Enter 键：

## HTML 页面的加载顺序

一旦浏览器收到页面请求的响应，它就会获取响应中提供的 HTML 标记并进行显示。本节将解释这是如何执行的，以及重新定位页面中某些 HTML 标签对其加载时间的影响。

一个 HTML 文档包含两个主要部分：头部（head）和主体（body），分别由`<head>`和`<body>`标签表示。浏览器通常会在响应消息中的数据仍在下载时就开始构建页面，从`<head>`部分开始，然后进入`<body>`部分。头部部分可能包含以下任何标签：`<style>`、`<link>`、`<script>`、`<meta>`、`<title>`和`<base>`。

除`<script>`之外的所有这些标签都只允许在`<head>`部分内，不允许在其他地方出现。这个规则告诉你，浏览器在渲染 HTML 的`<body>`部分之前需要了解些什么。如果你依次查看每个标签的描述，就应该明白为什么需要在处理`<body>`标记之前预先了解这些信息：

-   `<style>`：包含 CSS 样式定义，以便以自定义设计在页面上布局 HTML。浏览器需要知道如何在屏幕上显示标签之前进行布局，以防止出现难看的渲染效果。否则，浏览器会在应用自定义样式之前以默认样式绘制标签。`<style>`标签确保永远不会发生这种情况。

-   `<link>`：链接到外部数据。当引用外部样式表时，浏览器出于与需要知道`<style>`标签中的样式相同的原因，需要了解这些链接。当它适用于链接到站点内的其他文档时，它仅表示头部信息，与页面的主要内容分开。

-   `<meta>`：提供定义页面内容但独立于页面内容本身的数据。示例包括指定页面的关键字和描述，以供搜索引擎爬虫使用。也可以使用此标签执行与某些 HTTP 响应消息头值相同的操作——例如，为内容设置到期日期或指定内容类型。

-   `<title>`：指定页面的标题。这是出现在浏览器窗口标题、书签链接、搜索引擎结果和其他位置中的文本。

-   `<base>`：允许页面开发者为页面内容中指定的所有链接、图像和其他 URL 规定一个基础 URL。例如，如果`<base>`标签设置为指向`http://www.google.com/`，并且页面中的一个链接仅指定为`logo.gif`，那么浏览器将要查找的完整 URL 将是这两个 URL 的组合：`http://www.google.com/logo.gif`。

一旦浏览器读取了`<head>`部分并下载了其中所有必要的外部链接文件，它就可以开始顺序地、一个标签一个标签地读取和解析 HTML 文档的主体部分了。

### 识别性能中的潜在瓶颈

我们都希望浏览器能始终以最高效率加载页面请求：尽可能快地下载每一点数据，并在接收到每一块数据时立即将其渲染到屏幕上。不幸的是，实际情况并非总是如此。

在本节中，我将揭示一些可能导致页面加载效率低下的潜在瓶颈。目前，我不会提供这些缺陷的解决方案或变通方法；但请放心，在后续章节中，我会向你展示如何尽可能多地解决这些问题。

### 引擎马力

本章前面部分，我们探讨了存在于 Web 浏览器中的渲染引擎和 JavaScript 引擎，它们负责将 HTML、CSS 和 JavaScript 格式的简单文件转换为功能完整、可交互的网页。不同浏览器的引擎基于不同的底层代码构建，因此它们具有不同的性能特征，这并不令人意外。

通常，随着新版本的发布，浏览器制造商会修改底层代码以增强引擎性能，从而提升引擎效率。这使得当前主流 Web 浏览器的性能比以往任何一代都要好上数倍。

一般来说，终端用户使用的浏览器版本越旧，他们所经历的渲染和 JavaScript 性能就越差。

### 用户的上传速度

大多数用户通过 ISP（互联网服务提供商）以非对称连接的方式接入互联网。这意味着大多数用户可用的下载带宽远大于上传带宽；这两种连接速度并不相同。

带宽与下载或上传数据所需的速度成正比。

你可能会想，请求一个网页时需要从你的计算机上传哪些数据。事实上，从被请求页面链接的每一个外部文件——每张图片、每个样式表和 JavaScript 文件——在下载之前，都需要构建一个新的 HTTP 请求消息并发送到服务器。如果你的页面链接了大量外部文件（无论这些文件大小如何），你可能会发现用户的网络连接达到了上传限制，并且需要等待之前的请求发送完毕后，才能发送新的请求。互联网速度一直在提升，所以这个问题正在缓解，但仍值得对页面进行调整，以减少那些连接速度较慢的用户（例如移动用户）所遇到的困扰。

### 并行连接限制

许多浏览器都对可同时与每台服务器建立的连接数量设置了内部限制。一个现代 RIA（丰富互联网应用）页面，尤其是设计复杂的页面，可能包含超过 50 个外部文件引用需要加载才能完整渲染。对并行连接数量的限制，显然会限制页面下载并显示给用户的速度。
```

HTTP 1.1 规范建议同时连接数限制为同时下载两个文件。Opera 和 Safari 浏览器将此限制提高到四个。IE 8 则将其提高到同时下载六个。这些限制显然会制约浏览器的性能。如果所有文件都能同时下载，页面就能更快地呈现给最终用户。

### 图片格式的选择

历史上，Web 上盛行三种图片格式：GIF、JPEG 和 PNG。这些格式彼此差异巨大。在为页面编码图片时，如果选择了错误的格式，或采用了低效的压缩设置，就可能导致图片文件体积超出必要大小。由于大多数网页中图片的数量远超其他类型的文件，因此文件格式的选择应作为首要关注点。

### 不必要的内容

文件体积越大，下载到浏览器所需等待的时间就越长。在构建标记时，请确保没有引用不必要的样式表或 JavaScript 文件，也没有在页面中包含大段的注释。包含了不必要的代码，就意味着你冒着将永远不会使用的数据下载到用户浏览器的风险，这会增加完整页面渲染所需的时间。

### 缓存设置

一些 Web 开发人员选择在其 Web 浏览器中禁用所有缓存，以便始终拥有自己文件的最新副本进行测试。然而，大多数终端用户会保持其缓存设置为默认值，这通常意味着决定哪些内容被缓存以及缓存多久的规则，取决于传输内容的 Web 服务器的响应头。调整服务器，使其仅发送与先前类似请求相比有所更改的内容，可以确保浏览器需要接收的数据更少，从而为最终用户带来更快的体验。

### 未压缩的文本文件与多余空白

在构建和编写基于文本的 HTML、样式表和 JavaScript 文件时，空白字符的使用可能很重要。制表符间距、换行符、空格和注释有助于使代码更易于阅读、理解和维护。

每个制表符、换行符和空格字符都是浏览器有效渲染页面所不需要的数据。如果你能移除这些不必要的数据，文件大小将会减小，从而下载速度也会更快。

大多数浏览器和服务器都支持压缩算法，通常是 `gzip` 和 `deflate`，这些算法在传输时会压缩数据大小并移除所有不必要的字符，然后在接收端解压数据。如果没有压缩，文件体积会比实际需要的大，页面下载时间也会受到不利影响。

### 总结

本章描述了从 Web 服务器请求页面并将其发送到浏览器，然后将该响应转换为网页的过程，并重点指出了若干对此过程的速度和效率产生不利影响的因素。

在下一章中，我将揭示如何通过对 Web 服务器和代码进行特定更改，从而显著提升 Web 应用的性能，为你的最终用户提供更好的体验。

## 第 4 章：性能调优

上一章解释了浏览器和 Web 服务器如何通过消息相互通信，以及这些消息如何在网络中寻路到达正确的目的地。你还了解到，不同 Web 浏览器的性能因其渲染引擎和 JavaScript 引擎的不同而各异。

在本章中，我们将探讨如何让网页尽快“活起来”，以便访客能在他们的浏览器中使用它。研究表明，用户不会注意到良好的性能，但他们确实会因糟糕的性能而感到不快。人们期望网页在发出请求后就能立即加载。我们凭什么给他们低于预期的体验呢？这里的关键是效率——在最短的时间内将最多的数据下载到浏览器。

### 性能真的是一个问题吗？
