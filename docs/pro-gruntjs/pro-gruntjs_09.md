# 引言

那么，你拿起了这本标题略显独特的书，可能想知道什么是 `Grunt`，或者至少想知道过去两年间关于 Grunt 的种种热议究竟为何。简单来说，`Grunt` 是一个 JavaScript 任务运行器。其主要目标是自动化重复性任务，将开发人员的时间解放出来，以便专注于他们每天面临的更棘手的问题。

`Grunt` 基于 Node.js 以 JavaScript 编写，通过 `npm` 分发，由 Ben Alman（[`github.com/cowboy`](https://github.com/cowboy)）创建。自面世以来，`Grunt` 就提供了一个应用程序编程接口（API），允许开发者扩展并添加自定义任务以适应他们自身的流程。这种高度的可定制性使得 `Grunt` 变得极其流行，并拥有一个不断扩展的庞大生态系统。

作为一个任务运行器，`Grunt` 的核心概念之一是“任务”。每个任务都有一组可调的配置选项来满足你的特定需求。任务也可以有多个版本：例如，一套用于开发环境的配置，另一套用于生产环境。除此之外，`Grunt` 还提供了定义自定义任务的能力。自定义任务可以将现有任务组合成一个任务，或添加全新的功能。此外，`Grunt` 拥有文档齐全的 API，使开发者能够在运行时改变其任务运行器的行为。

贯穿全书，我们将使用 `Grunt` 来演示这个小巧但极其强大的工具如何优化你的开发工作流程。`Grunt` 常被描绘成前端工程师的专属工具；然而，我还会演示那些不完全是前端导向的项目如何也能从引入 `Grunt` 中获益。

#### 我如何从 Grunt 中获益？

`Grunt` 的主要优势和首要目标之一是自动化。当你现有的工作流程对你来说行之有效时，你可能会质疑为什么需要自动化。我希望这本书能起到鼓励作用，并演示自动化如何能让你更高效。

大多数开发者都熟悉执行代码检查、资源压缩、编译 CSS 等工作流程中所需的任务工具。然而，并非所有开发者都实现了流程自动化。一些团队选择使用持续集成作为构建应用程序和执行发布前检查的节点。这个环境通常由开发团队之外的人员控制，职责落在组织内部的其它部门。

依赖持续集成环境来执行构建任务是很便捷的。作为开发者，你编写代码，推送到中央代码仓库，然后持续集成（CI）服务器处理其余事情。但是，如果你需要在本地重现生产环境中的某个问题，那么这可能不是最快的方式。借助 `Grunt` 的强大功能，你可以在本地开发和 CI 环境中轻松使用相同的构建流程，从而缩短在本地构建应用程序生产版本所需的时间。

独立工作或在小团队中工作的开发者，如果选择使用命令行或图形用户界面（GUI）工具，可以通过使用 `Grunt` 来统一他们的构建流程。统一构建流程将简化项目设置和维护，因为只需遵循一个流程即可。

### 持续集成

如果你不熟悉 CI，这是一种常见的开发实践，即将来自一个团队开发者的代码合并到中央仓库。它通常用于运行单元测试、执行代码分析和自动化部署。大多数现代开源项目使用 `TravisCI`（[`travis-ci.org/`](https://travis-ci.org/)），这是一个开源 CI 环境，可以轻松与 GitHub 仓库集成。开发社区中其他流行的选择还有 `Hudson` 和 `Jenkins`，`Jenkins` 是 `Hudson` 的一个分支。`Jenkins` 和 `Hudson` 都有许多用于集成第三方工具或系统的插件，例如，一个插件可以实现在 GitHub 仓库有更新时触发构建。

#### 加速你的工作流程

有一些出色的工具和集成开发环境（IDE），它们提供了常见任务的工具，例如编译 CSS 和检查 JavaScript 代码，帮助你开发应用程序和网站。然而，这类工具通常需要初始设置，并且也可能导致工作流程脱节。

你可能想知道什么是“脱节的工作流程”。考虑以下场景：你正在开发一个非常简单的单页应用，它包含一组 JavaScript 文件、一个 CSS 预处理器和一些图片。在你发布应用程序之前，你必须进行 JavaScript 代码检查、编译 CSS 以及压缩图片。针对这些问题中的每一个，你都可以从现有的众多工具中进行选择，例如 `JSHint`、`LESS` 编译器 和 `pngquant`。你的 IDE 很可能会检查你的 JavaScript 代码并编译 LESS；但是，你还得切换到命令行去运行 `pngquant`。

在开发过程中，在浏览器、编辑器和命令行界面之间来回切换会让你分心，无法专注于必须解决的关键问题。`Grunt` 可以为你提供一个统一这些任务的解决方案。此外，`Grunt` 还能自动化这些任务，以便你可以专注于应用程序中特有的问题。

#### 每个工匠都需要一个工具带

不可否认，前端 Web 开发的技艺在过去几年发生了翻天覆地的变化。过去需要花费大量宝贵开发时间来解决浏览器兼容性问题的日子一去不复返了，因为开发者现在可以访问一套丰富的工具来处理此类琐事。利用这些工具，开发者可以将时间投入到解决应用程序中更复杂的问题上。解决日常任务的框架的出现，例如 `Bootstrap` 和 `AngularJS`，使开发者能够通过他们的应用程序提供增强的体验。

越来越多的用户通过移动设备访问应用程序，并期望 Web 应用程序能提供与原生移动应用程序相同的体验。来自移动设备的应用流量激增，也迫使开发者重新思考他们如何设计应用程序，从而增加了更多的复杂性。为了应对这种情况，开发者必须构建一套可反复使用的可靠工具。

`Grunt` 应当成为你工具带中的主要工具之一。由于 `Grunt` 的模块化特性，很容易构建一份可在多个项目中使用的任务配方手册。每个任务专注于解决一个特定问题，并且很容易跨项目混合搭配配置，为每种场景构建一套强大的工具集。

### 改进的前端工作流

不可否认，过去两年间前端工程师可用的工具已经取得了巨大进步。由社区大力开发的一个特定项目是 `Yeoman`。`Yeoman` 被定义为一种工作流而非框架，它包含三个关键组件：`Yo`、`Grunt` 和 `Bower`。`Grunt` 是 `Yeoman` 项目中的关键角色，正如本书后续所示，将 `Yo` 和 `Grunt` 结合使用，能够快速搭建包含自动化构建流程的项目。

#### 版本控制

使用 `Grunt` 的另一个关键优势在于，你的任务及其配置都会进行版本控制。由于项目中的 `Grunt` 任务是通过 `npm` 安装的，因此可以轻松地通过 `npm` 本身进行管理。除此之外，配置的变更对整个团队清晰可见，因为它们与项目一同进行版本控制。这构建了一套整个团队都能学习、开发并从中受益的工具集。

![Image](img/00006.jpeg) **注意** `npm` 是一个 JavaScript 包管理器，允许开发者轻松共享和重用 JavaScript 模块。`npm` 负责处理包的版本控制、依赖关系和发布。每个包都有一个在名为 `package.json` 的 JSON 配置文件中定义的元数据，其中包含名称、描述、版本、作者和依赖关系等信息。

#### 可读性

另一个促进 `Grunt` 快速普及的因素是其可读性。`Grunt` 的任务配置是一个简单的 JSON 配置对象，使其具有高度的可读性和可理解性。

`Grunt` 还推广了“不要重复自己”（DRY）的开发技巧，因为任务可以使用变量作为其配置的一部分。正如你将在本书后续内容中看到的那样，这也提高了任务配置的可读性。

拥有一个可读性强的任务运行器的另一个好处是，能够显著缩短新团队成员掌握构建流程工作原理所需的时间。

#### 替代方案

需要认识到，`Grunt` 并非首个用于自动化开发者工作流的任务运行器。有许多替代方案；然而，`Grunt` 凭借其庞大的生态系统、简洁性和速度，在其中脱颖而出。在深入探讨 `Grunt` 之前，我们将简要介绍几个流行的替代方案。

##### Ant

正式名称为 `Apache Ant`，“Ant”是一个基于 Java 的构建工具。任务不是使用 JavaScript 指定的，而是在项目中的 XML 文件中定义。`Ant` 附带超过 100 个内置任务，例如文件拼接、gzip 压缩文件以及替换文件中的内容。然而，这些任务更偏向于 Java 项目的构建流程。例如，如果你想支持 JavaScript 的 linting 检查，你必须包含一个新任务。要添加此类任务，`Ant` 要求将新任务编译成 JAR 文件，并从 XML 配置中引用。对于不熟悉 Java 的人来说，刚开始时这可能会有些令人生畏。如果你的项目在构建流程中不需要 Java，那么 `Grunt` 可能是更好的选择，因为引入 Java 会给项目增加不必要的依赖。

你可能会考虑选择 `Grunt` 而非 `Ant`，原因在于其使用的配置格式：JSON 而非 XML。阅读 `Ant` 的构建文件感觉有点臃肿，并且无法一目了然地看清构建流程如何整合，而 `Grunt` 的 JSON 更为精简，并且任务可以组合成逻辑名称。

##### Rake

`Rake` 是 Ruby 社区对 Make 文件的回应。`Rake` 允许开发者使用 Ruby 语法定义任务。任何使用过 `Ruby on Rails` 框架的人应该对 `Rake` 相当熟悉，因为它被用作执行诸如创建数据库、运行测试和编译静态资源等任务的首选工具。

`Rake` 没有任务配置的概念。相反，它选择定义并执行 Ruby 代码的任务来实现目标。例如，没有可用的配方或插件仓库来执行常见任务。如果你想拼接和 lint 检查你的 JavaScript，你必须从头开始编写你自己的任务，然后才能使用它。这显然会增加你开始项目的成本，因为 `Rake` 没有提供任何立即可用的东西。你需要确保你的任务高度可配置，以增加跨项目的重用性。

`Grunt` 通过提供广泛的插件选择来解决必须“重新发明轮子”的问题。此外，`Grunt` 还通过提供丰富的 API 来支持任务配置，从而推广了“配置优于代码”的概念。

##### Gulp

`Gulp` 是一个相对较新的工具，与 `Grunt` 一样，也基于 JavaScript。`Grunt` 和 `Gulp` 的另一个相似之处是基于模块的架构，并通过使用 `npm` 作为依赖管理器来驱动。`Gulp` 与 `Grunt` 一样易于上手；然而，可以说 `Gulp` 的任务定义更为简洁，因为任务是用代码而非配置来表达的。

已经有多篇博客文章将 `Grunt` 和 `Gulp` 进行对比。然而，也有相反的观点认为，这两个工具可以共存，因为它们在实现共同目标的方式上存在差异。`Gulp` 比 `Grunt` 更快，但由于其使用了 Node 流，入门门槛稍高。

![Image](img/00006.jpeg) **注意** `Grunt` 组合任务的方式是一个任务的输出会产生一个临时文件，该文件由下一个任务拾取进行处理。`Gulp` 不会产生这些临时文件；文件在各个任务之间通过管道传输。

### 总结

在本章中，你已经对 `Grunt` 是什么以及项目如何从使用它中获益有了基本了解。你还探讨了 `Grunt` 与现有类似替代方案的比较。本书将帮助你理解如何在项目中设置和使用 `Grunt`，使你能够快速地 lint 检查、测试和优化你的应用程序。
